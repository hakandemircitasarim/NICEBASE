NICEBASE is in solid shape architecturally, but the audit surfaced a tight cluster of high-impact issues that should land before the Play Store launch. After deduplication the 106 findings collapse to 34 actionable items (offline-sync-1 and correctness-2 are the same conflict-detection bug; security-7 and db-schema-4 are the same users INSERT policy; security-2 and db-schema-10 overlap on daily_question_answers; ai-aiya-1/4 are one crisis-handling workstream; a11y-1/2 and a11y-5/6/7/8/9/10/13 are batchable). Several findings were down-scoped from their original severity by the verdicts and I reflect that: the photo-base64 sync (correctness-1) is the single most damaging item (multi-MB base64 rows, large egress, upsert-failure risk) and is a true high. The crisis-safety gap (ai-aiya-1) is the only critical — a mental-health-adjacent app must not hand a suicidal-intent user a casual 'friend' reply with no hotline. The conflict/sync trio (conflict detection, client-clock watermark, daily-reconciliation race) is genuine silent data loss for multi-device users. Security real-wins are the users billing-column authz gap (self-grant premium/unlimited Aiya) and the aiya_chats missing FK (orphaned conversation data on account deletion, a GDPR concern given the just-added privacy policy). Order below: (A) crisis safety, (B) data-integrity sync + photos, (C) server-side cost/abuse + RLS, (D) DB migrations, (E) accessibility, (F) performance/bundle, (G) error-handling/i18n hygiene, (H) state/effects + code-quality polish. Items are grouped by file/area so they can be implemented in safe batches. Two corrections from the verdicts to honor at execution time: (1) the conflict fix must detect at PUSH time via optimistic concurrency OR run reconcile-before-push — the naive pull-branch-only condition does NOT fire because push runs first; (2) the memory-date display bug (db-schema-3) lives at the render layer (new Date(bareDate).toLocaleDateString in local TZ), so fixing only the mapper does nothing. Every migration item needs a YYYYMMDDHHMMSS file per CLAUDE.md 2.2, both-language i18n per 2.5, and a green npm run build per 2.18.
